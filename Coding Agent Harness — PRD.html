PRD: Autonomous Coding-Agent Harness

Event: LCC × DevClub — AI Coding Harness Hackathon Duration: 24 hours Team size: 3

1. Problem Statement

Build a harness around a standardized foundation model that can:

  • Understand a software-engineering issue
  • Navigate an existing repository
  • Use tools intelligently
  • Manage context effectively
  • Orchestrate model interactions
  • Recover from failures without human help
  • Produce correct, verified code changes
  • Use tokens and compute efficiently

Every team gets the same model, repo, issues, tests, and evaluation conditions. The differentiator is the harness — the engineering wrapped around the model, not the model itself.

2. Goals

Goal Why it matters
Solve issues end-to-end without human intervention Core definition of "autonomous" per the problem statement
Verify every fix against real tests before declaring done Judging criterion: "Correctness first," "Evidence over claims"
Recover visibly from at least one failure during the demo Proves the harness — not luck — produced the result
Report token/cost usage per issue Judging criterion: "Efficiency matters"
Keep the system small enough that all 3 team members understand the whole thing Needed for debugging under time pressure and for explaining design decisions to judges

3. Non-Goals (explicitly out of scope for 24h)

  • Multi-agent / multi-model orchestration
  • Custom fine-tuning of the foundation model
  • Full sandboxing/container isolation beyond what's needed to run tests safely
  • Support for multiple languages or multiple repos
  • A polished UI (CLI or minimal log view is sufficient)
  • Beating state-of-the-art SWE-bench scores — winning on rigor and demoability, not raw benchmark chasing

4. Approach

Base: Fork mini-swe-agent (SWE-agent/mini-swe-agent) rather than building the agent loop from scratch.

Rationale: ~100 lines of core Python, no forced tool-calling API, >70% SWE-bench Verified out of the box. Small enough for all three of us to read, own, and meaningfully modify in a day — unlike heavier frameworks (OpenHands) which would mostly be configured, not engineered.

What "our engineering" means on top of the fork: the stock repo has a deliberately dumb loop (bash-only, no compaction, no verification gating, no structured recovery). Our value-add is exactly the four subsystems below, layered onto that base. Git history from the fork point is our evidence of engineering effort for judges.

5. System Architecture

Issue → Orchestrator → Foundation Model ⇄ Tools/Repo
              ↓
        Context & Memory

Core loop (state machine): EXPLORING → EDITING → TESTING → (DONE | RETRY | ESCALATE)

6. Functional Requirements by Subsystem

6.1 Orchestration & Recovery — Owner: Person A

  • Drive the state machine; decide when a task is complete, when to retry, when to escalate
  • Detect repeated identical failures (same error twice) → force a strategy change on next attempt
  • Enforce a hard step cap per issue (e.g. 8 attempts); on cap, emit a structured "blocked" report (what was tried, last error, best guess at cause) instead of looping indefinitely
  • Own main.py — the integration point that calls into Context and Tools as defined interfaces

6.2 Context & Memory — Owner: Person B

  • Maintain a persistent scratchpad (hypothesis, files touched, attempt history) that is summarized — not raw-dumped — back into the prompt each turn
  • Compact/drop stale tool outputs once superseded (e.g. old test failures once a newer result exists)
  • Track and log token usage and cost per issue and per run
  • (Stretch) lightweight repo symbol index built once at start, reused across issues

6.3 Tools, Repository Exploration & Verification — Owner: Person C

  • Implement: read_file(path, line_range), search_code(pattern), edit_file(diff), run_tests(target)
  • Repo navigation strategy: start from issue text (error strings/symbol names), grep outward rather than loading full repo
  • Verification: run the real test suite after every edit; report both (a) does the target failing test now pass, and (b) did any previously-passing test regress
  • No self-graded "looks correct" — test suite output is the only accepted evidence of success

7. Interface Contract (agreed at Hour 0, before parallel work begins)

Shared data shapes all three subsystems code against, so each person can stub the other two and build independently:

  • ToolResult: { success: bool, output: str, error: str | None }
  • ScratchpadState: { hypothesis: str, files_touched: list[str], attempt_history: list[str] }
  • VerificationResult: { passed: bool, failing_tests: list[str], stdout: str, stderr: str }

8. Team & Timeline

Window Activity
Hr 0–1 Agree on interface contract (Section 7), together
Hr 1–14 Parallel build on owned subsystems, using stubs for the other two
Hr 14–18 Integration — swap stubs for real implementations
Hr 18–21 Debug on real provided repo/issues; tune prompts
Hr 21–24 Buffer + demo prep: stage the run that shows explore → edit → fail → adapt → pass; prepare token-usage numbers

9. Success Metrics (for our own tracking, ahead of judging)

  • % of provided issues resolved with passing tests, no regressions
  • At least one demoed run showing failure → recovery → success
  • Tokens and wall-clock time per issue, reported per run
  • Zero infinite loops / hangs during live demo

10. Risks

Risk Mitigation
Integration breaks late because interfaces drifted Small, frequent merges to shared repo (not one big merge at Hr 14); ping team immediately on any contract change
Demo issue happens to succeed on first try (no recovery to show) Pre-stage a known-tricky issue where the model's first attempt plausibly fails, to guarantee the recovery beat
Time lost on mini-swe-agent internals Timebox exploration of the base repo to first 1–2 hours; if not understood by then, simplify further
Test suite is slow, throttling iteration Scope verification to the relevant test file/target, not full suite, where possible

11. Open Questions for Organizers

  • Does "your own harness" permit forking an existing open-source agent repo, or must the harness be built from scratch?
  • What weight does the rubric place on efficiency vs. correctness vs. recovery demonstration?
  • Is there a fixed issue set for evaluation, or will judges run held-out issues live?
